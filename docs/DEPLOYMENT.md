# Deployment Guide

How to put EduNexus online using free tiers. Frontend on **Vercel**,
backend on **Render**, database on **Neon**, uploaded files on
**Cloudflare R2**.

Neon is used rather than Render's own Postgres because Render deletes
free databases after 30 days, which would silently break a portfolio
link. Neon's free tier does not expire.

Follow the steps in order — the CORS step at the end depends on knowing
the Vercel URL, which does not exist until step 5.

---

## 1. Database (Neon)

1. Create a project at [neon.tech](https://neon.tech). No card required.
2. Copy the **pooled** connection string.
3. Convert it for SQLAlchemy and require TLS:

   ```
   postgresql+psycopg2://USER:PASSWORD@HOST/DBNAME?sslmode=require
   ```

   Note the `postgresql+psycopg2://` scheme and the `?sslmode=require`
   suffix. Both are needed.

Neon suspends compute after five minutes idle. The app enables
`pool_pre_ping`, so the first request after a suspension reconnects
instead of failing.

## 2. Schema and demo data

Run once from your machine, pointed at Neon:

```bash
cd backend
export DATABASE_URL='postgresql+psycopg2://...?sslmode=require'
../.venv/bin/alembic upgrade head
../.venv/bin/python scripts/seed.py
```

Seeding is idempotent and makes no AI calls, so it is safe to re-run.
It creates:

| Role | Email | Password |
|---|---|---|
| Teacher | `teacher@edunexus.demo` | `Demo1234!` |
| Student | `priya@edunexus.demo` | `Demo1234!` |
| Student | `tom@edunexus.demo` | `Demo1234!` |
| Student | `sofia@edunexus.demo` | `Demo1234!` |

Plus a Biology classroom (join code `BIO101`) with three published
lessons, five linked concepts, a five-question quiz, and per-student
mastery and gamification history.

## 3. File storage (Cloudflare R2)

1. Create an R2 bucket in the Cloudflare dashboard.
2. Create an API token with object read/write on that bucket.
3. Keep the account ID, access key ID, secret, and bucket name.

Without these the app falls back to local disk, which works locally but
loses uploads on every redeploy.

## 4. Backend (Render)

Create a **Web Service** from the repo. `render.yaml` supplies the
runtime, build and start commands, the pre-deploy migration step, and the
`/health` check.

Set these in the dashboard (they are declared `sync: false` so no
credential is committed):

| Variable | Value |
|---|---|
| `DATABASE_URL` | The Neon URL from step 1 |
| `GEMINI_API_KEY` | From [Google AI Studio](https://aistudio.google.com/apikey) |
| `R2_ACCOUNT_ID` | From step 3 |
| `R2_ACCESS_KEY_ID` | From step 3 |
| `R2_SECRET_ACCESS_KEY` | From step 3 |
| `R2_BUCKET` | From step 3 |
| `CORS_ALLOW_ORIGINS` | Placeholder for now, e.g. `https://example.com` |

`APP_SECRET_KEY` is generated by Render. `APP_ENV=production` is set in
`render.yaml`, and startup **refuses to boot** if the secret key is still
the default or if the database and CORS values point at localhost.

Confirm the service is healthy:

```bash
curl https://YOUR-SERVICE.onrender.com/health
# {"status":"ok","database":"ok"}
```

## 5. Frontend (Vercel)

Import the repo and set:

- **Root directory**: `frontend`
- **Environment variable**: `NEXT_PUBLIC_API_BASE_URL` =
  `https://YOUR-SERVICE.onrender.com`

This value is inlined at build time, so it must be set **before** the
build. Changing it later requires a redeploy, not just a restart.

## 6. Close the CORS loop

Go back to Render and set `CORS_ALLOW_ORIGINS` to your real Vercel
domain, then redeploy:

```
https://your-app.vercel.app
```

The API sends credentials, which forbids the `*` wildcard — every origin
must be listed explicitly. Add custom domains as extra comma-separated
entries. Both sides are HTTPS; pointing the frontend at an `http://`
backend causes browsers to block every request as mixed content.

## 7. Keep the backend awake

Render suspends a free service after 15 minutes idle, and waking takes
roughly a minute. The app shows a "waking the server" notice so this does
not look like a failure, but a pinger avoids it for most visitors.

Point [cron-job.org](https://cron-job.org) or UptimeRobot at:

```
https://YOUR-SERVICE.onrender.com/health
```

every 10 minutes. Render's free allowance of 750 hours per month covers
roughly one always-on service, so a single pinged service fits.

## Verifying the deployment

Work through this against the live URL:

1. Load the site — the landing page renders.
2. Sign in as `teacher@edunexus.demo`.
3. Open the seeded classroom; lessons and the quiz are listed.
4. Generate a lesson — exercises the real Gemini path.
5. Sign in as `priya@edunexus.demo`; the dashboard shows XP and badges.
6. Open the knowledge graph — five concepts with prerequisite links.
7. Take the quiz and confirm scoring.
8. Upload a document to a lesson, then download it — confirms R2.
9. Hard-refresh a deep link such as a lesson page — confirms dynamic
   routes resolve without a client-side navigation.
10. Visit a nonsense URL — the custom 404 appears, not Next's default.
11. Leave it 20 minutes, then reload — the waking notice appears and the
    app recovers rather than erroring.

## Notes and limits

- **Free tier storage**: Neon gives 0.5 GB and R2 gives 10 GB. Ample for
  a demo; not sized for real classroom use.
- **AI quota**: Gemini's free tier is rate limited. AI routes are capped
  at 20 generations per user per hour so one visitor cannot exhaust it.
- **Sessions**: tokens are held in `localStorage` and expire after two
  hours. There is no refresh token or server-side revocation.
- **Rate limits are per process**: the limiter is in-process, which is
  correct for the single free-tier worker but would need a shared store
  if the service is ever scaled out.
- **Rotate keys** before making the repository public. No secret has ever
  been committed, but live keys sit in your local `backend/.env`.
